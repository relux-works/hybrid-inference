## Verified findings

### F1 - major: response backpressure prevents another client from reaching the fair scheduler

- **Location:** `tools/hybrid/prefill.cpp:91`; admission at `tools/hybrid/prefill.cpp:102`; response delivery at `tools/hybrid/prefill.cpp:201`; write timeout at `tools/hybrid/prefill.cpp:90`.
- **Failure scenario:** client A starts four valid critical extends, receives each 200 response header, then pauses reading their approximately 20 MB delta bodies. All four HTTP workers remain occupied writing those responses. Client B's critical extend cannot enter `request_scheduler::enter` at all, even though the four A prefill handlers have completed and released their scheduler leases. Its request receives no headers until an A response worker is released. The configured write timeout allows a stalled response to occupy a worker for a long period. Round-robin selection inside the scheduler cannot protect a client that never reaches its queue.
- **Verification:** an isolated instance of A's existing binary, four A-owned response sockets held under controlled TCP backpressure, then one B-owned critical extend. The B socket remained pending during the bounded negative observation; closing one A reader allowed the *same* B request to return 200 and commit exactly one token. A separate run reproduced the same admission failure with B's session-list request. No request-rate benchmark or throughput claim is involved.
- **Suggested fix:** separate admission/control handling from blocking binary response delivery, or enforce bounded per-client admission before the shared HTTP pool so one client cannot occupy every worker. Add an actual HTTP backpressure regression with a critical request from another client. Increasing the pool size alone merely moves the failure threshold. The pure `next_request` starvation regression should remain, but does not cover this path.
- **Evidence:** `.temp/hybrid-b-r2-261030/http-probe-02.log` and `probe_http_critical.py`; initial control in `http-probe-01.log` and `probe_http.py`. Both probe commands exited 0. Node logs and recorded owned PIDs are `probe-node-02.log` / `probe-node-02.pid` and `probe-node-01.log` / `probe-node.pid`.

### F2 - minor for the current 8k prototype: accepted context sizes exceed the delta header's token budget

- **Location:** `tools/hybrid/hybrid-state.cpp:88` and `tools/hybrid/hybrid-state.cpp:99`; advertised context limit at `tools/hybrid/prefill.cpp:62`; accepted input at `tools/hybrid/prefill.cpp:169`; serialization after prefill at `tools/hybrid/prefill.cpp:187`.
- **Failure scenario:** configure `N_CTX=16384` and send 10,000 valid six-digit token IDs in one critical extend from n0=0. The input fits both the context and the 1 MiB request limit, but its required delta JSON header is 70,412 bytes, exceeding the writer's 65,536-byte limit. The node performs the prefill and returns generic HTTP 400 instead of a delta. The identical token sequence succeeds as a shadow extend, which omits the large token-bearing response header. Thus a caller cannot offload some turns inside the context range the node advertises. The existing <=8192-token goldens fit, which bounds this finding's current milestone impact.
- **Verification:** existing A binary, one isolated 16k context, a synthetic 10,000-token request using an in-vocabulary token ID. Critical extend returned 400; n/hash and snapshot remained unchanged. The identical shadow extend was accepted and produced n=10000 with the independently computed prefix hash. A separate compact-JSON size calculation confirms the header length and cap mismatch. The positive shadow control asserted acceptance and final state; its 202 response is the status selected by the reviewed handler, rather than a separately captured assertion in that probe.
- **Suggested fix:** agree a bounded header limit that covers the node's advertised maximum turn/context and apply it consistently in writer and reader, or publish a smaller per-extend limit and provide a contract-compatible chunking path. In either case validate the header budget before inference and return a specific error. Add a positive large critical-extend control, alongside a deliberate over-limit rejection with unchanged state.
- **Evidence:** `.temp/hybrid-b-r2-261030/header-probe-01.log`, `probe_header_budget.py`, `header-budget-01.json`, and `header-probe-node-01.log`. The runtime probe exited 0. This is a functional correctness control, not a prefill benchmark.

Within the admitted queue, the first ticket of each (client, session) is eligible; the starvation fix rotates eligible clients before prioritizing critical work within the chosen client.
